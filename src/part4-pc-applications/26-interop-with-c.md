# Interop with C

Chapter 17 introduced `unsafe extern "C" { ... }` and `#[repr(C)]` as a
preview. This chapter is the full workflow: compiling a real C source file
as part of your crate's build, binding to it by hand, and the ABI details
(struct layout) that make it safe to do so.

## Compiling C as part of the build: `build.rs` + the `cc` crate

A `build.rs` file is an ordinary Rust program Cargo runs *before*
compiling your crate — the direct analogue of a Makefile rule that
compiles a `.c` file into a `.o` before the final link step, except Cargo
runs it for you automatically, with no separate `make` invocation. The
[`cc`](https://crates.io/crates/cc) crate wraps the actual C compiler
invocation:

```rust,ignore
{{#include ../../examples/ch26-interop-with-c/build.rs:build_rs}}
```

`cc::Build` finds a working C compiler on the host (`cc`, `gcc`, or
`clang` — the same ones you already have on any machine that builds C)
and produces a static library Cargo links into the final binary
automatically. The C source it compiles is ordinary C:

## `#[repr(C)]`: making the layout promise explicit

```rust,ignore
{{#include ../../examples/ch26-interop-with-c/src/lib.rs:repr_c_point}}
```

Chapter 8 mentioned that a plain Rust struct's field layout is
**unspecified** — the compiler is free to reorder fields, insert padding,
or otherwise lay things out however it finds most efficient, because nothing
outside the Rust compiler is supposed to depend on it. That's exactly
backwards from what you need at an FFI boundary: `geometry.c`'s `point_t`
has `x` then `y`, each a 4-byte `float`, with C's ordinary layout rules.
`#[repr(C)]` is Rust's way of saying "lay this struct out exactly the way
a C compiler would" — without it, passing `Point` to `point_distance` would
be relying on undefined behavior that happens to work today and might not
tomorrow.

## The binding itself

```rust,ignore
{{#include ../../examples/ch26-interop-with-c/src/lib.rs:extern_block}}
```

This is hand-written, not generated by
[`bindgen`](https://crates.io/crates/bindgen). `bindgen` parses a C
header and generates the `extern "C"` block (and any `#[repr(C)]` structs)
for you — genuinely the right tool when you're wrapping a large, existing
C library you didn't write and don't want to transcribe by hand. It also
needs `libclang` discoverable at build time, which isn't guaranteed in
every environment this book gets built in, so this repository's examples
and exercises stick to hand-written bindings for small, self-authored C
files, where there's nothing to transcribe from and no extra build-time
dependency to risk.

Every `unsafe extern "C"` item you don't mark `safe fn` is implicitly
`unsafe fn` — call it from an `unsafe { }` block with a `// SAFETY:`
comment, same convention as Chapter 17. Marking an item `safe fn` (as
above) is a promise that it's sound to call with *any* input of the
declared type; only do that when it's actually true — `point_distance`
and `clamp_int` can't do anything unsound no matter what floats/ints you
pass them, so marking them `safe` is honest, not a shortcut.
